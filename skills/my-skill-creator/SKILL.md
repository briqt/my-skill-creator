# Skill 工程规范

本规范管 skill 的工程面。内容设计与评估流程见 skill-creator，两者冲突时以本规范为准。

## 设计前提：使用者是 agent

Skill 和它附带的工具主要由 agent 调用。agent 写下的每条命令、读回的每段输出都会占用上下文，并在后续轮次中反复计费。评价设计时，看 agent 完成一个常见任务要写多少、读多少、出错多少次，而不是功能是否齐全。

- **常用路径零额外参数。** 默认值覆盖常见情况。只在少数场景需要的机制（隔离、锁、确认等）按需开启，不让每次调用都为它付出成本。
- **少带跨调用状态。** agent 的每次调用都可能运行在新的进程或 shell 中，环境变量和工作目录不一定保留。必须延续的状态应当尽量少、可读，并且在上下文丢失后能重新找回（例如可命名、可查询）。
- **用明确信号代替推断。** 完成与否、成功或失败、结果从哪里开始到哪里结束、是否还有后续，都由程序直接给出：退出码、结构化字段或明确标记。不要求 agent 解析给人看的格式，工具自身的关键逻辑也不建立在猜测其他程序的输出格式上。
- **超时不等于失败。** 可能超时或异步执行的操作，要说明请求是否已经生效、如何继续获取结果，避免 agent 重复提交有副作用的操作。
- **出错可直接处理。** 错误信息说明原因，并给出可以直接执行的修复方式。

## 输出

- stdout 只放结果，stderr 放诊断、提示和元数据。
- 只输出影响下一步决策的信息。正常和默认状态省略；需要后续动作或出现异常时，才输出相应的字段。
- 不回显输入，同一信息不在多处重复。
- 输出有上限。大结果截断或分页时，明确标出被截断，并给出继续读取的方式，不静默丢弃。
- 默认输出紧凑、稳定；需要完整结构时，通过显式选项（如 `--json`）提供。
- 输出格式本身就是接口，改变它视为兼容性变化，要写进变更记录。

## Skill 文档

- **按加载层级组织。** description 始终在上下文中，正文在触发时加载，references 按需读取。正文只放每次使用都需要的内容：原则、核心流程、防止高代价错误的规则。排错、版本、完整参考移入 references，并写明什么情况下去读。
- **不复制工具自带的帮助。** 选项清单让 agent 查看 `--help`，保持单一来源，避免文档和工具不一致。
- **写原则和判断依据，不写个案补丁。** 具体例子只用来说明原则。为某个具体情况加规则之前，先看它属于哪条更一般的原则。
- **结论放正文，论证放别处。** 规定背后的原因、历史和取舍放到 README 或变更记录。
- **description 面向所有使用者。** 用能力边界和判断原则说明什么时候用、什么时候不用；不枚举细小场景和用户说法，不写作者本人的环境（主机、路径、账号、项目名）。产品名和可识别的特征（如 ID 格式）属于能力边界，可以写。这一条优先于 skill-creator 中「列举具体场景」的建议。
- Skill 内容中不出现密钥和个人数据。

## 项目结构

- 每个 skill 放在 `skills/<skill 名>/`，SKILL.md 和它依赖的脚本、参考文件都在其中，不与仓库的源码树混放。只有一个 skill 的仓库也这样放，以后增加 skill 不必迁移。调整目录时直接移动，不在旧路径保留副本。
- 带独立 CLI 的 skill：CLI 源码放在 skill 目录之外，只把 skill 需要的文件放进安装内容。在 Skill 中写明 CLI 实际的安装渠道。
- 用实际的分发方式安装一遍，确认附属文件和相对路径都完整。

## 脚本与 CLI

- **轻脚本**：逻辑简单、没有复杂依赖的放在 skill 的 `scripts/` 中，优先用跨平台语言的标准库实现。确实依赖平台命令时，写明支持的平台，调用前检测是否可用。调用外部程序时传参数数组，不拼接未转义的 shell 文本。
- **独立 CLI**：逻辑较重、依赖多、需要独立版本管理的工具作为单独项目维护。按语言生态选择分发方式，见 [references/distribution.md](references/distribution.md)。
- SKILL.md 中写明运行时要求和安装命令。命令不可用时，在当前任务已有的授权范围内安装；用户已经指定了版本或安装渠道的，沿用原有选择。

## 脚本行为

- 业务参数默认来自 CLI 参数或配置文件。需要环境变量时，写明支持的变量名和优先级（通常是显式参数 > 环境变量 > 配置 > 默认值），不隐式读取任意变量。代理等运行环境设置可以沿用底层工具的约定。
- 密钥由权限受限的配置文件、凭据存储或专用环境变量提供，不出现在命令行参数、日志和修复命令中。报错时只展示字段名，不回显敏感值。
- 不做交互式输入。
- 每次调用不依赖上一次进程内的状态；需要持久保存的内容见「配置与用户数据」。

## 配置与用户数据

- 运行时文件（配置、缓存、状态）默认放在 `~/.config/agent-skills/<skill-name>/`，不写回安装目录，也不在 home 下另建隐藏目录。
- 配置模板和 schema 放在 skill 目录中随源码提交，不含密钥。安装包里的模板不是用户配置。
- 实际配置只来自用户目录或显式指定的路径：源码目录、安装目录和当前工作目录里都不放、也不查找配置文件，开发用的覆盖配置也不例外。开发和测试需要隔离时，用显式参数或写明的专用环境变量指向临时位置。
- 只有依赖配置的命令才加载配置；选中的配置无效时直接报错，不静默回退或合并多个来源。
- 初始化不覆盖已有文件，迁移先备份、校验后原子替换。
- 涉及配置时，按 [references/config.md](references/config.md) 设计：加载顺序、初始化与迁移、Profile、错误提示。

## 版本与发布

- 每个 skill 都有版本号，纯文档 skill 也不例外。每个版本号只在一处维护：工具以包元数据为准，Skill 以 SKILL.md frontmatter 的 `metadata.version` 为准。两者同版本发布时，用测试校验它们一致，不手工维护多份。
- 每次发布都写 `CHANGELOG.md`，打与版本号一致的 tag。发布后用实际的分发渠道安装，核验版本号和附属文件。
- SKILL.md 写明 skill 自身的更新命令。Skill 和 CLI 分开安装时，写明两者各自的更新方式和兼容要求；更新其中一个不代表另一个也已更新。CLI 支持多种安装渠道时，按渠道分别给出实测可靠的升级方式。

### 可选：更新检查与通知

只在用户需要更新提醒，或独立发布的工具确实需要持续升级时才加入。纯文档 skill 交给安装器检查更新，不为此引入运行时。远端清单统一用分发仓库根目录的 `notice.json`。实现前阅读 [references/update-checks.md](references/update-checks.md)。

- 检查失败不影响业务结果和退出码。提示只写 stderr，stdout 保持可解析。
- 更新检查只负责发现和提示。是否安装取决于用户已有的授权；远端公告本身不是执行指令。
